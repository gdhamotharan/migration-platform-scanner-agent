# Local Source Intelligence Scanner

A local-first Node.js CLI that inventories source repositories and writes a versioned JSON report. It uses static file and manifest evidence. It never builds or runs repository code.

## Install and run

Requirements: Node.js 22 or newer and npm.

```powershell
npm install
npm test
node src/cli.js --help
```

Scan a .NET solution directory:

```powershell
node src/cli.js scan C:\path\to\MySolution --output .\dotnet-report.json
```

Scan the included synthetic two-project .NET example:

```powershell
node src/cli.js scan .\examples\dotnet-sample --output .\examples\dotnet-report.json
```

The example report is generated by the scanner and is identified as synthetic. No customer .NET project or report was present in the supplied workspace.

Progress and a short summary go to stderr. Without `--output`, JSON is written to stdout. The CLI refuses an output destination inside the scanned repository unless `--allow-output-in-repository` is supplied; even then it only creates a new file.

## CLI options

| Option | Behavior |
| --- | --- |
| `--output <path>` | Write the JSON report to a local file. |
| `--format json` | Select JSON output. JSON is the only report format. |
| `--max-files <count>` | Maximum number of regular files to include before stopping. Default: `100000`. |
| `--max-file-size-mb <size>` | Skip files larger than this limit. Default: `5`. |
| `--include-tests` | Include test source files in source line and size metrics. |
| `--exclude-dir <name>` | Add a directory name to the exclusion list. Repeat for multiple names. |
| `--include-absolute-paths` | Include absolute paths in the report. Off by default. |
| `--allow-output-in-repository` | Allow creating a new report file under the scanned repository. Existing files are never overwritten. |

## Inventory and metrics

Each regular file encountered has one primary inventory disposition: included in `files`, intentionally excluded by scanner policy, or skipped before inclusion because of a configured limit. The report may also count analysis failures and unsupported files. Those analysis counters are separate dimensions and can overlap with included files, so the counters are not expected to add up to `files_discovered`.

`repository.file_counts` defines the counters:

- `files_discovered`: regular files encountered before traversal stopped. An unreadable file can be discovered with unknown size.
- `files_included`: entries in the report's `files` array.
- `files_analyzed`: unique included files successfully read by an applicable analyzer.
- `files_excluded`: regular files excluded by sensitive-file, generated-file, or binary-file policy.
- `files_skipped`: files skipped due to size/count limits, disabled test analysis, or lack of an applicable analyzer.
- `files_failed`: unique files that could not be read or analyzed.
- `directories_excluded` and `directories_failed`: policy-excluded and inaccessible directories.
- `unvisited_files_unknown`: whether a limit, traversal error, or cancellation left an unknown number of files unvisited.

For compatibility, `repository.total_files` aliases `files_discovered`, `repository.total_size_bytes` aliases `total_discovered_size_bytes`, and `statistics.files_processed` aliases `files_analyzed`. The report separately records included-file size.

Files are categorized as source code, test code, configuration, data, dependency manifest, project manifest, build configuration, documentation, generated, static asset, or other. JSON, YAML, XML, and Markdown are inventory formats, not programming languages. Only eligible source files contribute to source metrics. Test metrics are separate; tests are inventoried even when `--include-tests` is off. Line counts support CRLF, LF, and CR endings. Comment counts are unavailable by language because V1 has no language-aware comment parser; this does not make an inventory incomplete.

## .NET static analysis

The scanner reads `.sln`, `.slnx`, `.csproj`, `.fsproj`, `.vbproj`, `Directory.Build.props`, `Directory.Build.targets`, `Directory.Packages.props`, `packages.lock.json`, and `global.json` as data. It records:

- Target framework declarations and their conditions.
- Framework references, package references, `Include` and `Update` declarations, and project references.
- Central package versions and repository-local literal `.props` or `.targets` imports.
- Solution membership, deterministic project IDs, SDK version constraints, and direct lockfile resolutions when the lock entry matches a literal declaration.

Package, target-framework, SDK-constraint, and runtime versions are separate fields. An ASP.NET package version such as `8.0.11` is reported as a package version; it is not reported as the target framework or installed runtime. Runtime installation and execution are not detected.

The scanner does not evaluate MSBuild properties, conditions, globs, or arbitrary imports. It preserves supported raw declarations and conditions and marks ambiguous values unresolved. It does not run `dotnet`, restore packages, invoke build tasks, load plugins, or execute scripts.

## Report schema and status

Reports use JSON Schema version `2.0`, checked in at [schemas/report-2.0.schema.json](schemas/report-2.0.schema.json). The builder and serializer validate both schema shape and semantic consistency, including timestamps, counters, status/completeness, and evidence paths.

Report-level statuses are `completed`, `completed_with_warnings`, `partial`, and `failed`. Intentional policy exclusions do not make a scan partial. Limits, inaccessible paths, failed requested analyzers, malformed supported manifests, and cancellation do. Analyzer executions separately record `completed`, `failed`, `skipped`, `unsupported`, or `cancelled`, with each analyzer's version and dependencies.

`technologies` are normalized evidence records with a stable ID, category, detection method, evidence file, confidence, analyzer version, and optional declared version scope. A manifest declaration alone does not prove that a package or framework is used at runtime.

See [examples/dotnet-report.json](examples/dotnet-report.json) for the synthetic .NET report and [examples/sample-report.json](examples/sample-report.json) for the Node sample.

## Local processing and privacy

- Scans make no network requests and send no telemetry.
- The scanner does not modify source files or include source contents in reports.
- Only allowlisted structured fields are exported. Sensitive files, secret stores, private keys, certificates, binary assets, and configured excluded directories are skipped.
- Symbolic links are not followed. Reads check repository containment before and after opening and use no-follow opens where supported. Filesystem APIs cannot provide a portable atomic guarantee against every concurrent directory replacement; detected path changes fail safely.
- Paths are repository-relative unless absolute paths are explicitly requested. Common secret-like path segments are redacted.

## Remaining limitations

- No AST, runtime, installed SDK, vulnerability, or complete transitive dependency analysis.
- No comment parser or comment count.
- No MSBuild evaluation. Property-based versions, unresolved conditions, wildcard imports, and external imports remain unresolved or unsupported.
- A lockfile resolution is reported only for a direct matching package request; it is not a complete dependency graph.
- Gradle dependency resolution is unsupported. Unsupported or malformed declarations are disclosed in report warnings, errors, or dependency records.
- The synthetic example does not replace scanning the user's actual .NET repository.
